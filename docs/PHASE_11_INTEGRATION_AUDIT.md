## 1. Current Implementation and Integration Flow

### Architecture Overview

Two Add-In entry points coexist in the same application bundle:

| Entry Point | Context | Registration | Responsibility |
|-------------|---------|--------------|----------------|
| Custom-Page Add-In | Browser tab (iframe within MyGeotab) | `geotab.addin.opexVehicleBooking` | UI rendering, booking CRUD, notification record creation |
| Service Add-In | WebWorker background | `geotab.addin.service` | Polls AddInData for pending notifications, delivers native toasts, updates delivery status |

### Data Flow

```
Booking Event (custom-page)
    ↓
NotificationEngine creates AddInData record (delivery_status: "pending")
    ↓
Service Add-In polls AddInData every 30s
    ↓
service.notifications.show() delivers native toast
    ↓
Service Add-In updates delivery_status to "delivered" via api.call("Set", ...)
```

### Persistence

- **MyGeotab AddInData** is the only persistent storage mechanism (no external databases)
- **localStorage** is used only in DEMO mode (standalone browser outside MyGeotab)
- AddInId scopes all AddInData records to this Add-In

## 5. Potential Runtime and Lifecycle Issues

### Issue 1: Service Add-In Bundle Not Generated by Build Pipeline

**Severity:** High

The `vite.config.ts` has no entry point for `service-addin.js`. The bundle must be compiled separately and hosted at the URL specified in `geotab/opex-vbm-service-config.json`. Without this file at the correct URL, the Service Add-In cannot load.

**Current workaround:** Manually compiled to `apps/web/dist/service-addin.js` via `tsc`.

### Issue 2: AddInId Availability in Service Add-In Context

**Severity:** High

The Service Add-In runs in a WebWorker and looks up the AddInId from `localStorage` (key: `opex-vbm-addin-id`). This key is set by the custom-page app when the user saves the AddInId in the UI. If the custom-page app has not been opened and configured first, the Service Add-In cannot find the AddInId and will not deliver notifications.

### Issue 3: `api.call` Style Inconsistency

**Severity:** Medium

- `addinDataProvider.ts` (custom-page): Uses callback-style `api.call(method, params, success, error)`
- `serviceAddin.ts` (Service Add-In): Uses Promise-style `service.api.call(method, params)`

Per official documentation, the Service Add-In SDK uses Promise-style API calls. The custom-page SDK uses callback-style. These are different contexts with different SDK contracts, so this inconsistency is expected but should be documented.

### Issue 4: Native Notification Delivery Only in Service Add-In Context

**Severity:** Medium

`service.notifications.show()` is only available in the Service Add-In WebWorker context, not in the custom-page Add-In context. The `showNativeNotification()` function in `notificationService.ts` correctly returns `"failed"` when called from custom-page context (no `service.notifications` available). Delivery status updates are handled by the Service Add-In polling loop instead.

### Issue 5: Race Condition on Delivery Status

**Severity:** Low

If two Service Add-In instances poll simultaneously, both could attempt to deliver the same pending notification. However, MyGeotab runs one Service Add-In instance per database, so this is unlikely. No explicit locking is implemented.

### Issue 6: Polling Stops When Browser Closed

**Severity:** Low

Service Add-Ins run in WebWorkers within the MyGeotab page context. When the browser is closed or the user logs out, polling stops. Notifications created while offline remain `"pending"` until the Service Add-In next runs.

## 8. Notification Processing Reliability

| Concern | Status | Mitigation |
|---------|--------|------------|
| Duplicate notification prevention | Implemented | Idempotency key per `(eventType + bookingId + recipient)` |
| Idempotency behavior | Implemented | `findByIdempotencyKey()` checks before `createNotification()` |
| Multiple Service Add-In instances | Low risk | MyGeotab runs one instance per database |
| Concurrent polling | Low risk | Single interval per Service Add-In instance |
| Delivery status transitions | Implemented | `pending` → `delivered`/`failed` via Service Add-In polling |
| Failed notification retry | Implemented | Failed notifications remain `pending` for next poll cycle |
| Stale pending notifications | Implemented | Polling retries every 30s indefinitely |
| API rate-limit handling | Not implemented | No rate-limit tracking or backoff |
| Error handling and logging | Implemented | Errors swallowed; Service Add-In never crashes |
